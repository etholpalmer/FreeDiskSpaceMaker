User Guide · F# · macOS / Linux / Windows

DiskCleanupAdvisor

Finds disposable files on a developer machine, explains item by item why each is (or is not) safe to remove, and — only when you explicitly ask — moves the safe ones to the Trash.

✓

The one thing to remember: this tool moves files to the Trash and never deletes them. A scan with no arguments only reports. Nothing is modified unless you pass --delete and then type yes. Even then, items go to the Trash with a generated restore script — and your disk space is reclaimed only when you empty the Trash yourself.

01What it is

DiskCleanupAdvisor is a single F# script, run with dotnet fsi. It walks your home directory and the well-known cache locations a developer machine accumulates — package-manager caches, browser caches, build artifacts, logs, crash reports, duplicates, large files — and produces a report grouped by category, each finding tagged with a risk level and a plain-English reason.

It is deliberately conservative. It understands the difference between a regenerable cache and the data a running application depends on, and it refuses to treat the second as the first. Its defining constraint, which every design decision is subordinate to, is that it must be impossible to lose data by using it.

There is no build step, no NuGet restore, and no third-party dependency — only the .NET base class library.

02Requirements & install

You need the .NET 10 SDK (F# 9 and dotnet fsi ship with it). The tool runs on macOS, Linux, and Windows via RuntimeInformation platform detection, though the macOS rule catalogue is the most complete; Linux and Windows catalogues are seeded and grow as they can be verified on real machines of those platforms.

There is nothing to install beyond cloning the repository. From the project root:

dotnet fsi DiskCleanupAdvisor.fsx -- --help

The -- separates dotnet fsi's own arguments from the script's. Every example below includes it.

macOS: grant Full Disk Access

Without it, macOS silently blocks the tool from reading parts of ~/Library, and the scan is incomplete. The tool detects this and reports how many directories it could not read — see footgun #5. Grant access to your terminal under System Settings → Privacy & Security → Full Disk Access.

03Quick start

A plain scan is the default and is completely safe — it reads and reports, and cannot modify anything:

# Dry run (default). Reports only. Nothing is touched.
dotnet fsi DiskCleanupAdvisor.fsx -- --scan

# Write a browsable HTML report alongside the console output.
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --html report.html

# When you have reviewed the report and want to act:
# prompts first, moves only Safe-rated items to the Trash.
dotnet fsi DiskCleanupAdvisor.fsx -- --delete

Read the report, decide, then — if you want — delete. The tool never gets ahead of you.

04Risk levels

Every finding carries one of five risk levels. Only the first is ever removed automatically; the second only with --force. The rest are reported for your judgement and are never deleted by the tool.

LevelIconMeaningAuto-deleted?
Safe✓ Regenerable, no user data. The producing tool recreates it on demand. Yes, with --delete
ProbablySafe○ Regenerable, but an application may need to re-download it, or it may hold a locally-built artifact. Only with --delete --force
Review? Requires human judgement — may be application state, documents, or a copy something depends on. Never
Dangerous! Deletion is likely to break something. Never
NeverDelete✕ Protected. The tool will never remove it, and no flag overrides this. Never
Why duplicates and node_modules are only Review

Identical bytes do not make a copy disposable — the second copy may be the one a running program references. And node_modules is reinstallable only if the project is still wanted and its lockfile is intact. The tool reports both, prominently, but will not remove them for you.

05The three-gate safety model

Before any file is moved, it must pass all three independent gates. Each gate can only reject — none can approve on its own.

GATE 1Rule assertion A matching rule must mark the path Safe and deletable. Absent a rule, the answer is no.
→
GATE 2Allowlist anchoring The path must be a strict descendant of the rule's resolved root, checked after normalisation — so ../ escapes resolve first.
→
GATE 3Denylist veto A hardcoded protected set — Documents, Desktop, /System, anything inside a .git directory — checked last. It outranks --force and config overrides.

The veto has no bypass flag. Configuration risk overrides can only raise a rule's risk, never lower it; an override that tries to lower risk is rejected as a configuration error. Symlinks are never followed, and the tool refuses to run as root unless you pass --allow-root.

Built so the dangerous case is unreachable, not just guarded

Internally, the only value that reaches the deletion step is one the risk engine itself minted after all three gates passed. There is no code path that hands an arbitrary path to the deleter — "delete this path I chose" is simply not expressible. That is a stronger guarantee than a runtime check you have to remember to write.

06Warnings & footguns

None of these can cause data loss on their own — the safety model prevents that — but each is a place where the tool's honest behaviour can surprise you if you expect something else.

1The Trash is not emptied, so space is not freed yet

--delete moves files into the Trash. Your free space does not change until you empty the Trash yourself. A report that says "Moved 15 GB to the Trash" has reclaimed nothing on disk — it has made 15 GB eligible to be reclaimed.

Do: empty the Trash in Finder when you are satisfied. That — not the tool — is the irreversible step.

2Emptying the Trash is the point of no return

Everything the tool does is reversible until you empty the Trash. The tool will never empty it for you, by design. Once you do, the restore script (footgun #9) can no longer bring anything back.

Do: skim the Trash before emptying, especially on your first run.

3Sparse files: the real size is smaller than it looks

Docker and Podman disk images are sparse — their logical length is far larger than the blocks they actually occupy. The tool reports allocated size (what you reclaim), not apparent size. A Docker.raw that macOS lists as 64 GB may really be 16 GB on disk, and the tool will say 16 GB. This is correct, but it can look like an under-count if you compare against ls -l.

Know: du -h <file> agrees with the tool; ls -l shows the inflated apparent size.

4Time Machine snapshots pin freed space

On macOS, a local Time Machine snapshot can hold on to the blocks you just freed, so emptying the Trash appears to reclaim nothing. The tool reports any snapshots it finds and prints the tmutil commands — but it will not run them.

Do: if free space does not move after emptying the Trash, inspect and thin or remove the snapshots with tmutil — worked examples below.

Working with local snapshots — tmutil

tmutil ships with macOS. These are local snapshots on your boot volume — separate from your Time Machine backup disk, which none of these commands touch. All of them need no special privileges to list; deleting may prompt for your password.

1 · List snapshots on a volume

tmutil listlocalsnapshots /
Snapshots for disk /:
com.apple.TimeMachine.2026-10-26-093035.local (dataless)
com.apple.TimeMachine.2026-10-27-204125.local

The timestamp in each name is YYYY-MM-DD-HHMMSS — here, one snapshot from 26 Oct 09:30:35 and one from 27 Oct 20:41:25. (dataless) means the system has already partially purged that snapshot's data under disk pressure; it still holds metadata and is worth removing explicitly to release it fully.

2 · List just the dates (handy for scripting)

tmutil listlocalsnapshotdates /
Snapshot dates for disk /:
2026-10-26-093035
2026-10-27-204125

Same information, stripped to the bare date stamps — exactly the form the delete command below expects.

3 · Delete one snapshot by date

tmutil deletelocalsnapshots 2026-10-26-093035
Deleted local snapshot '2026-10-26-093035'

Pass the date stamp only — 2026-10-26-093035, not the full com.apple.TimeMachine.… name. A date argument deletes the snapshot with that timestamp on every mounted disk that has one.

4 · Delete every local snapshot on a volume

tmutil deletelocalsnapshots /
Deleted local snapshot '2026-10-26-093035'
Deleted local snapshot '2026-10-27-204125'

Giving a mount point instead of a date removes all local snapshots on that volume. This is the blunt "reclaim it all now" option.

5 · Thin snapshots to free a target amount

# Ask macOS to free ~20 GB (20 × 1024³ = 21474836480 bytes), urgency 4 (most aggressive).
tmutil thinlocalsnapshots / 21474836480 4
Thinning local snapshots on disk / ...
com.apple.TimeMachine.2026-10-26-093035.local

The gentlest option: purge_amount is in bytes, urgency is 1–4 (higher is more aggressive). macOS removes the oldest snapshots until it has tried to free that much, and prints which it thinned. It may free less than requested if fewer snapshots exist.

Before you delete

Local snapshots are macOS's short-term "undo" for your whole volume — they back recovery of recently-changed files between full Time Machine backups. Removing them is safe and routine when you need the space, but you lose those intermediate restore points until the next snapshot is taken. DiskCleanupAdvisor reports snapshots and prints these commands; it never runs them, because a snapshot delete is a system-level action outside its trash-only model.

5A partial scan is not a complete one

Without Full Disk Access on macOS, whole subtrees are unreadable and silently excluded by the OS. The tool surfaces this — "N directories were unreadable" — rather than pretending the scan was total. The reclaimable figure is a floor, not a ceiling, until access is granted.

Do: grant Full Disk Access (section 2) for a complete picture.

6Your biggest consumers are often not deletable

VM images, iOS Simulator device data, and node_modules are frequently the largest things on a dev machine, and the tool rates them Review — reported but never auto-removed. The headline "reclaimable" number is almost always smaller than the headline "pending review" number, and that is correct.

Do: use the right purpose-built tool for those — docker system prune, xcrun simctl delete unavailable, or removing a VM machine explicitly. (See footgun #10 for a Podman trap.)

7--force is narrow, and the veto still wins

--force widens automatic deletion by exactly one level — it also permits ProbablySafe. It does not touch Review, Dangerous, or NeverDelete, and it does not bypass the protected-path veto. There is no flag that deletes "everything".

Know: if you expected --force to clear Review items, it will not. That is deliberate.

8--delete alone takes the whole Safe set

Filters like --age and --min-size narrow what is reported — and therefore what --delete acts on. --delete with no filters moves every Safe-rated item. If you meant "only caches older than 90 days", you must say so; the tool will not assume a narrower intent than the flags express.

Do: combine filters with --delete, e.g. --delete --age 90, when you want a narrower set. The confirmation prompt shows the count and total size before you commit.

9A file that changed since the scan is skipped, not moved

Between the scan and your yes, you might sit at the prompt for a while. Immediately before each move the tool re-checks the file: if its size, type, or link status changed, or it is now inside a protected location, it is skipped and reported as a failure — never moved blindly.

Know: "N items could not be moved" after a delete is usually this — something wrote to a cache while you were deciding.

10Podman: system prune will not reclaim the machine image

If the tool flags a Podman machine image, note that podman system prune cleans up inside the guest VM — it does nothing while the machine is stopped, and even a successful prune leaves the host file the same size, because freeing blocks inside a sparse image does not return them to macOS. The directory also survives a Homebrew/Desktop uninstall, because the official .pkg installs to /opt/podman.

Do: reclaim it with podman machine rm <name>, which destroys the guest filesystem — genuinely irreversible, unlike anything this tool does.

11The default JSON report is capped; --json-full is enormous

--json writes the 50 largest findings and marks the document truncated (findingsTruncated: true) while keeping every aggregate total accurate. A full scan has well over 100,000 findings, so --json-full can produce a 100 MB+ file.

Do: use --json for a quick machine-readable summary; reach for --json-full only when you genuinely need every row.

12Windows refuses --delete rather than guessing

Moving to the Recycle Bin needs a platform call this script-only tool does not make, and the only dependency-free fallback would be an irreversible unlink — which would defeat the whole safety model. So on Windows, --delete returns an error instead of degrading to something unsafe. Scanning and reporting work normally.

Know: this is a refusal on purpose, not a bug.

07Ten worked examples

01A plain, safe scan
dotnet fsi DiskCleanupAdvisor.fsx -- --scan

The default mode. Walks your disk, prints a console report grouped by category with a risk badge on every finding, and ends with "This was a dry run. Nothing was modified." You can run this as often as you like with zero risk.

02Only old items
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --age 90

Reports only findings at least 90 days old, on top of whatever age floor each rule already applies. Good for "show me the stale stuff, not last week's caches". An age of 0 (the default) is a no-op — it changes nothing.

03Only large items
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --min-size 104857600

Reports only findings of at least 100 MB (the value is in bytes). Turns a 150,000-item report into the handful of things actually worth your attention.

04Find duplicates
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --duplicates

Adds a "Duplicate files" section. Detection is a three-stage funnel — group by exact size, then a sampled hash, then a full hash only on survivors — so it is affordable even over a huge tree. Duplicates are reported as Review and their wasted space is shown as its own figure; they are never turned into deletion candidates.

05A dedicated largest-files view
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --large-files

Adds a top-50 largest-files section beyond the default summary. Useful when a single file, not a category, is the problem.

06A browsable HTML report
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --html report.html

Writes a self-contained HTML report — no external resources, opens offline — with search, sort, and filter over the findings and SVG charts by category. This is the best surface for deciding what to remove before committing to a delete.

07JSON for tooling — capped vs full
# Compact: aggregates + 50 largest findings, marked truncated.
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --json report.json

# Complete: every finding. Can exceed 100 MB on a full scan.
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --json report.json --json-full

Both carry the true totals, category breakdown, and duplicate groups. The capped form adds findingsTruncated: true so a consumer is never misled into thinking a partial document is complete.

08Actually reclaim space
dotnet fsi DiskCleanupAdvisor.fsx -- --delete

Scans, prints the report, then shows "About to move N items (X GB) to the Trash" and waits for you to type yes. Only Safe items are moved. Each goes into a timestamped folder in the Trash with its original directory structure preserved, and a restore script is written to reports/restore-<timestamp>.sh before the first move.

09A narrowed, forced delete
dotnet fsi DiskCleanupAdvisor.fsx -- --delete --force --age 60

Moves both Safe and ProbablySafe items — but only those at least 60 days old. The protected-path veto still applies; Review and above are still untouched. Read the confirmation count carefully before typing yes.

10Undo a delete
sh reports/restore-2026-10-30-143022.sh

Every --delete writes a restore script. Running it moves each item from the Trash back to its original location. It refuses to overwrite an existing file, recreates missing parent directories, never deletes anything, and is safe to re-run — a second run reports what it skipped rather than clobbering. This works right up until you empty the Trash.

Bonus — choose the hash algorithm, or use a config file 
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --duplicates --hash-algorithm md5
dotnet fsi DiskCleanupAdvisor.fsx -- --scan --config ~/my-cleanup.json

--hash-algorithm (sha256 default, or md5 for speed on trusted local data) only affects duplicate detection. --config points at a JSON file — see the next section.

09Configuration file

Configuration is JSON, loaded from --config <path>, else ~/.config/diskcleanupadvisor/config.json, else built-in defaults. Every value is optional. Validation reports all problems at once rather than failing on the first.

{
  "ignorePaths":      ["~/Projects/active"],
  "ignoreExtensions": [".psd", ".sketch"],
  "minSizeBytes":        1048576,
  "findingsMinSizeBytes": 0,
  "ageThresholdDays":     30,
  "hashAlgorithm":        "sha256",
  "riskOverrides":        { "Homebrew Cache": "Review" }
}
KeyMeaning
ignorePathsPaths excluded from scanning entirely (~ is expanded).
ignoreExtensionsExtensions excluded from results, lower-cased with a leading dot.
minSizeBytesFloor for hashing and duplicate detection.
findingsMinSizeBytesFloor for what appears as a finding (the config form of --min-size; default 0).
ageThresholdDaysThe config form of --age.
hashAlgorithmsha256 or md5.
riskOverridesMap of rule name → new risk level. May only raise risk.
Risk overrides are raise-only, on purpose

You can make the tool treat a Safe rule as Review, but you cannot make it treat a Review rule as Safe. An override that tries to lower risk is rejected as a configuration error — the config cannot be used to talk the tool into deleting something it would otherwise protect.

10Reports

The console report always prints. The three file formats are additive and render from the same scan result — no format sees data another lacks.

  • Console — colour-coded, grouped by category, with the two space figures kept distinct (see below).
  • HTML (--html) — self-contained, dark-mode aware, searchable and sortable, with SVG charts. The best surface for deciding.
  • JSON (--json) — machine-readable; capped by default, complete with --json-full.
  • Markdown (--markdown) — for pasting into notes or a ticket.
Two space figures, never one

Every report shows reclaimable (eligible for automatic removal) and pending review (needs your judgement) as separate numbers, and never adds them. Conflating them would let you believe space was freed when it had only been listed. When duplicates are enabled, their wasted space is a third, separate figure — also never summed into the others.

11Restoring what you moved

Each --delete produces three things, all written before the first move so a crash mid-run still leaves an accurate record:

ArtifactWhat it is
~/.Trash/DiskCleanupAdvisor-<timestamp>/ The moved files, with their original directory structure mirrored beneath — so restoring is pure path arithmetic, and two files sharing a name never collide.
reports/deletions-<timestamp>.json A journal: every item's path, rule, size, and timestamp.
reports/restore-<timestamp>.sh A shell script that moves everything back. Refuses to overwrite, recreates parents, never deletes, safe to re-run.
 
# Undo a run — works until you empty the Trash.
sh reports/restore-2026-10-30-143022.sh
Earlier builds flattened the Trash — current builds do not

A historical version moved files into the Trash by basename alone, which discarded their structure and made restoring to the original locations impossible. Current builds mirror the full path and generate the restore script above. If you are on a build without the DiskCleanupAdvisor-<timestamp> folder, update before relying on restore.

12Adding a rule

Rules are plain data. The scanner is parameterised over the rule list and contains no rule-specific logic, so adding a rule is appending a record to src/Rules.fsx — no other file changes. Two invariants are enforced by tests:

  • Only a rule at risk Safe may assert SafeToDelete = true (a helper sets both together so they cannot drift apart).
  • No deletable rule may target a user-data directory.

Rules are matched most-specific-first by resolved root length, which is how a narrow Safe rule can live inside a broad Review one — the exact mechanism that keeps sandboxed app data under ~/Library/Containers protected while still cleaning the cache subpaths within it.
